# Stage

The scaled pixel grid a game lives in: its native size (320 by 214 by
default) times a scale, centred in the window. Everything inside positions
in stage pixels (`--px`) and sizes text in em. It fits itself to the
viewport, goes tall on a phone held upright, and tells the pieces inside
through `usePixels()`.

## Anatomy

1. **Section**, `width` by `height` times the scale, in the ground colour
2. **Layer**, the full grid inside it: moved up by `crop`, down by `lift`
3. **Turned screen**, instead of all of it on a phone held sideways (`turned`)
   or in a window too small for the screens' words (`small`)

## Fitting the viewport

Without `scale` the stage measures the window (`Fitted` shows it; the
others pin the scale so they do not fight Storybook's frame):

| Window                  | Stage                                                                      |
| ----------------------- | -------------------------------------------------------------------------- |
| Wide                    | 3x where it fits with a 24 px gutter, else what the width or height allows |
| Dense screen            | The scale snaps to whole device pixels (`crispScale`), never under 2.25x   |
| Between device pixels   | The origin snaps too: moved under a device pixel onto the nearest one      |
| Short                   | `crop="fit"` takes up to 60 rows of ceiling off the top before it shrinks  |
| Held upright (portrait) | Tall: the window's width, the height of the small viewport, `rows` rows    |
| Fullscreen              | No gutter, all of it fits                                                  |
| Phone on its side       | `turned`, if given, else the stage                                         |
| Too small (under 2.25x) | `small`, if given, else the stage at 2.25x, wider than the window          |

A crisp stage pixel is only crisp on screen when the stage also starts on a
whole device pixel. Where it starts is up to the page: the centring, what sits
above it, and the scroll, which Chrome keeps in whole CSS pixels (at 1.25 and
1.5, the usual Windows scaling, those fall between device pixels). So the stage
measures where it is in the viewport and moves itself by the remainder with
`translate` (`useSnap`, `snapOffset`), again after every scroll, resize and
change of the device pixel ratio. It does so only when the scale is crisp and
the ratio is above 1: at 1x the browser snaps the box itself. What is laid over
the stage (dialogs, notes) is absolute inside it and moves with it; nothing in
it may be `position: fixed`.

The pure maths is `scaleFor`, `fitFor`, `tallFor`, `crispScale`, `crisp`,
`backingFor`, `snapOffset` and `fontSizeFor` in `foundations/scale`, all but
`snapOffset` taking the native size.

## What it provides

`usePixels()` gives `scale`, `tall`, `rows`, `crop`, `crisp`, `backing` (the
scale to draw a canvas at), `turn` and `small`. The stage sets `--px`, `--bui-bar`
(the tall bar's height, `bar` CSS pixels, else 0) and the font size, and
`data-layout="tall"` for the `tall:` variant.

## Usage

- **Do** give a game one stage, with every screen inside.
- **Do** fill `turned` with the ask to turn the phone, and `small` with
  the ask for a bigger window, each with a fullscreen button if the game
  has one and the screen fits it (`fullscreenFits()`).
- **Do** use `lift` on the tall stage to centre a group in the rows it does
  not need.
- **Don't** set sizes in CSS pixels inside it, except for touch targets.
- **Don't** use `scale` in a game: it is for docs and workbenches (a fixed
  stage is never tall and never turned).

## Input

Focusing the stage, or tapping it, centres it in the viewport. It has no
keys of its own: a game binds them with `useKeys`.

## Accessibility

- A `<section>` named by `label`
- It takes focus from a tap (`tabIndex={-1}`) so the page does not scroll
  away from the game
