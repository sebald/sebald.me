# Building components

How the kit's components are made and what their props mean, so a new one
fits the rest without a review to tell it how. The JSX says what something
does; how it looks follows from that.

## A component is what it does

- **Name it by what it does or is**, never by how it looks or where it
  sits: `Line` (a line of a conversation), `Text`, `Tabs`, not `Muted`,
  `Loud` or `CornerLegend`.
- **A new component only for new behaviour.** Different state, logic,
  semantics or keys make a new component: `Heading` (it is in the page's
  outline), `ScreenTitle` (drawn in the bitmap letters), `IconToggle` (it
  has a pressed state). A different look of the same thing is a `variant`
  of it: a hint and a call to act are both `Text`.
- **It owns its behaviour.** What it does over time, it does itself: a
  `Meter` blinks with `blink`, a `Timer` counts down from `remaining`; the
  game doesn't toggle a look on a timer of its own.

## Props

| Prop                  | Means                                                                                    | Example                                               |
| --------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `variant`             | The kind of thing by its use. It implies the rules: `primary` is the one a screen is for | `Button variant="destructive"`, `Text variant="call"` |
| `size`                | How much room it takes                                                                   | `Button size="small"`                                 |
| A state, as a boolean | A yes or no, named for the state, never for the look                                     | `disabled`, `pressed`, `past`, `blink`                |
| A choice, as a string | One of named options: `left` or `right`, never a boolean for one of them                 | `Step points="left"`                                  |
| Content               | `children`, the words or the parts                                                       | `<Tab value="pm">PM</Tab>`                            |

- **`variant` and `size` only**, with defaults, and the default is the
  common case. No `tone`, `kind`, `type` or `on`. A variant names a use,
  not a colour (`secondary` is the other side, not "ember") and never a
  place (no `variant="bar"`).
- **A variant only when something needs it.** No look for "maybe
  later": `Tabs` have one look, the window's, until a screen needs tabs
  without a window. One look is less to keep consistent.
- **No raw style values as props.** No opacity, colour or pixel offset:
  name what it is for and let the component decide the value.
- **Strings for a choice, booleans for a fact.** A boolean is only for
  a yes or no (`disabled`). Where it would pick one of two or more
  options (`left` for a way it points) or where several booleans
  describe one thing between them, it is one string naming the options
  (`points: 'left' | 'right'`): it reads at the call site and cannot
  hold a combination that makes no sense.
- **The options written out in the type.** A prop that picks from options
  is a union of its values in the props interface
  (`variant?: 'primary' | 'secondary'`), never derived from the styles
  (`VariantProps`, `keyof typeof`): the declaration, a hover and a type
  error then name the values. The cva variants are checked against it
  (`satisfies Record<NonNullable<ButtonProps['variant']>, ClassValue>`),
  so a value missing from either side fails the type check.
- **No booleans that change the structure.** If a prop would render other
  parts or other logic, it is another component, or parts you compose.
- **Every component takes `className`**, merged last, for the one-off
  placement on a screen; never to restyle it into something else.

## Composition

- **Children, not props, for parts.** A part is a child in the JSX, never
  JSX passed through a prop (`legend={…}`, `tabs={…}`, `start={…}`):

  ```tsx
  <Tabs defaultValue="pm">
    <TabList aria-label="Pools">
      <Tab value="pm">PM</Tab>
    </TabList>
    <TabPanel value="pm">
      …
      <Legend keys={[['←→', 'pool']]} touch="Tap a tab" />
    </TabPanel>
  </Tabs>
  ```

- **Compound components share state through context.** The root holds the
  state that concerns all parts (`Tabs`' value); the parts read it and take no prop for it.
- **The look is shared by internal parts, not by exported styles.** A tab's
  panel and a `Dialog` are drawn by the same `WindowFrame` as a `Window`,
  so there is no `Window` to put in them: their parts go straight in. A
  window in a window is never right, and the Blip visual tests fail on one
  in any story. Style objects are
  not part of the kit's API.

## Placement: the parent places, the child marks itself

Learned from React Aria and Marigold, which do the same with slots.

- **Every component marks its root** with `data-slot="<name>"`
  (`data-slot="legend"`, `"icon-button"`). A test fails on one that
  doesn't.
- **A child places nothing.** It has its own look (a legend is small and
  dim), never its position in one parent.
- **The parent places and styles its children by their slot**, in its own
  styles: a window's body puts a legend along its bottom edge
  (`*:data-[slot=legend]:mt-auto`), the stage puts one in its corner. So
  the same `<Legend>` works anywhere, and a new parent adds its own rule.
- **A named slot says what a child is, not where it goes.** Where the
  parent has places for different kinds of children, the child names its
  kind with `slot` and the parent decides the place:
  `<IconButton slot="leave">` goes where `Controls` puts what leaves the
  screen (the start), the rest to the end. The rule lives in one parent,
  not in every screen.
- **Context for what a child must know to behave.** Where CSS can't do it,
  the parent tells its children through context, never through a prop the
  caller has to repeat: `Controls` tells its buttons whether they are on
  the bar (label and a thumb-sized icon) or in a corner.
- **Keys go to the top layer.** A part that listens for keys checks
  `useOnTop()` when one comes in; a `Dialog` opens a layer
  (`useKeyLayer`) and gives it to its parts, so the screen under it hears
  nothing without a flag of its own.
- **State as data attributes**, which the styles read: Base UI's
  `data-active` on a tab, `data-layout` on the controls.

## Shared parts

Learned from React Spectrum and Marigold, whose containers share their
parts by role.

- **A part that recurs across containers is one shared part**, named by
  its role: `Title`, `Content`, `Actions`. Not a `DialogTitle`,
  `WindowTitle` and `TabPanelTitle` that differ in a level and a class;
  never a place (`Footer`, `Header`).
- **The container says what the part can't know, through context**
  (`PartsContext`): the element that draws it there (a dialog's title is
  its name). A window's or a dialog's title also names a menu in it
  (`NamedByTitle`): one id the container makes, the `Title` wears and a
  `Picker` points at, so a menu needs no second name to keep in step.
  Only meaning goes through context,
  never a look and never a place.
- **The container places the parts by their slot**, in its own styles,
  as with any child: the window's body puts room under a title and above
  the actions.
- **A part works anywhere**: outside a container a `Title` is a heading.
  Nothing throws, and `Content` clears the context, so what the caller
  nests in it is never taken for the container's parts.
- **A new container checks these first.** If it has a title, something it
  says or things to do, it takes the shared parts and provides the
  context; a part of its own only for a role no other container has.

## Lists of items

Children over arrays of data: a menu built from `<PickerItem>`s reads like
the screen it makes, and each item's kind is its `variant` (`accent`,
`back`). An item registers itself with its list through context, and the
list takes the order from the DOM, so items work inside groups and inside
a screen's own components. What belongs to an item, its description box,
the item renders itself.

## Motion: a UI element or game art

Two kinds of motion, told apart by what moves.

- **A UI element moves smoothly.** A window, a menu, a bar, the stage
  itself: a CSS transition, so it can be interrupted, on the kit's curves,
  `ease-bui-out` for what enters, leaves or answers the player and
  `ease-bui-in-out` for what moves across the stage. It names the
  properties it animates (never `transition` or `transition-all`) and
  stays at 300 ms or under. `opacity` for a fade; for a move by whole
  stage pixels, `translate` (`calc(var(--bui-px)*n)`), which rests on
  whole device pixels; for a size, or a move whose result would rest
  between device pixels, the layout's own properties (`top`, `left`,
  `width`, `height`), which land on whole device pixels where a scale or
  a clip draws between them and blends the art's edges.
- **Game art moves like a sprite.** A character, a title slamming in, a
  blink, the stage jolted by a hit: keyframes, stepped (`steps()`), in
  whole stage pixels and whole frames. The kit's are `animate-bui-*`
  (`blink`, `enter`, `appear`, `shake`, `thud`, `flash`); the game holds
  one back to its own moment with `animation-delay`.
- **Not every change moves.** What the arrows do, the cursor going down a
  list, a row lighting up, happens at once: list navigation doesn't
  animate.
- **Reduced motion**, `motion-reduce:`: what moves snaps, and a fade may
  stay.

New or changed motion follows the `emil-design-eng` skill
(emilkowalski/skills: should it animate at all, its purpose, easing,
duration) within these rules; where they are stricter they win. The layout
properties above are for a move that would rest between device pixels on
pixel art; a move by whole stage pixels (`translate` of `calc(var(--bui-px)*n)`)
rests on whole device pixels at every scale measured (2.25x, 3x, a phone's
1.256x, at 1x and 2x device pixels) and may use the transform.

A game's own art follows the same rule in its own stylesheet; where a
piece of art glides on purpose, its comment says why.

## Focus

One mark for "you are here", the menus' cursor in the primary colour, and
a table of each control's look and its ratios (`foundations/focus.mdx`).

- **The cursor on everything a player steps through.** A `Picker` row, a
  `Button`, an `IconButton` and a `Field` (left of its label) show it; a
  new control does too, pointing at its name. A control may add a second
  cue inside its box that changes colour, never size (a field's underline
  turns gold). Only the exceptions
  the focus page lists (`Tab`, `TabPanel`) keep a line or a frame.

- **Nothing grows.** A focused control is exactly as big as an unfocused
  one: `bui-focus` is an outline one `--bui-px` thick with a negative
  offset (a frame inside the edge), `bui-focus-line` an underline of the
  label, a field's underline turns gold, the cursor sits in room the
  layout leaves for it (a row's cursor column, `Actions`, `Content`'s form
  rows 8 in). No outline with a positive offset, no ring that adds
  a pixel, no fill that lifts.
- **One mark whatever the fill.** A control that comes in several colours
  (`Button`'s variants), or sits over any scene (`IconButton` in a corner),
  takes a mark outside its face, the cursor, not one per colour: that is
  how games mark a selected button. Every button shows it.
- **A cursor has room.** 3 stage pixels from what it points at, nothing
  else it could point at closer than 6 on its side, clear of its frame:
  side by side, focusable things are 12 apart (`foundations/focus.mdx`,
  the cursor's room). The visual tests check it in every story.
- **Primary, or its inverse.** The mark is the primary colour (3:1 against
  the window, WCAG 1.4.11). Where the control's own face is the primary
  colour (the key), the mark is the letters' colour on it
  (`--bui-focus-color`).
- **Never colour alone.** A line, a cursor or a thicker line appears where
  there was none (WCAG 1.4.1, Xbox
  [103](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)),
  and it must not rely on a hue a player may not tell apart.
- **A new control picks its row in the table**, with its ratios, and
  `foundations/uniformity.test.ts` fails on a focus style outside it.

## Orient on games, not only the web

Web conventions answer how a control works in a browser. A game screen is
also played with a d-pad or a thumb, where every row is a stop for one
cursor and nothing has a pointer or a Tab key. When building a component,
a screen or a pattern, check the game side first and the web side second,
and where they differ say which one the component follows and why.

- Xbox Accessibility Guidelines, one page each:
  [112 navigation](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112)
  (a menu is fully usable by directional input, logical focus order,
  linear menus loop, the same prompts on every screen),
  [101 text](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101)
  (size and legibility),
  [102 contrast](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/102),
  [103 additional channels](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)
  (never colour or sound alone).
- [Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/):
  a checklist by level (basic, intermediate, advanced) of what a game
  should offer, for a quick check of a screen against the whole.
- [Unity UI navigation](https://docs.unity3d.com/Packages/com.unity.ugui@1.0/manual/script-SelectableNavigation.html):
  how a directional move finds the next control (automatic from layout or
  explicit), and that a control that uses a direction itself cannot be
  left with it.
- [Godot GUI navigation and focus](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html):
  focus as the model, per-direction neighbours, Tab as a secondary path.
- [Unreal widget navigation](https://dev.epicgames.com/documentation/en-us/unreal-engine/widget-navigation-in-unreal-engine):
  the same idea in UMG, with rules per widget (explicit, wrap, stop).
- [Game UI Database](https://www.gameuidatabase.com/): screenshots of real
  games' screens by kind (settings, inventory, shop, save), for what a
  screen of that kind holds. The site blocks scripted requests; open it in
  a browser.
- [WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/): the web
  side, the roles, names and keys a control needs for a screen reader
  (its [keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
  page says what Tab and the arrows each do).

The research behind the form controls, with what is sourced and what is
from memory, is `docs/blip-harness/research/forms-and-navigation.md`.

## Examples

A use of the kit that a consumer could copy (a menu, a duel, a toggle with
its state) is an **example**, not JSX in a story: a `.tsx` file in an
`examples/` folder next to the page, one component per file, named for what
it shows (`dialog/examples/options.tsx`, id `dialog/options`), with a doc
comment that says it in a line. It imports the kit by relative path like
any source file; the pack step rewrites those imports to `@sebald/blip-ui`
in `docs/examples/`, and fails on one a consumer could not write (a story,
another example, a name `index.ts` does not export). A composition story
renders the example (`render: () => <PairExample />`, aliased where the
story has the same name) and keeps only what Storybook needs around it: the
stage in a decorator, controls, tags. A page's `<Canvas>` of that story
becomes the example's source in `blip docs`, so the story and the page show
one thing. `Default` and `Overview` stay stories. An example does not
import from a story and no story repeats an example's JSX. Pattern pages
(`src/patterns/<name>/<name>.mdx`) are the same, with their examples in
`src/patterns/<name>/examples/`. A sheet that is only for checking the kit
(`compositions/mood-board.tsx`) has no page and is no example: it sits next
to its story, outside `examples/`, since every `examples/` folder needs a
page of the same name (CI builds the docs and fails on one without).

## Checked by tests

`foundations/uniformity.test.ts` fails on spacing written as a number
instead of a role (`foundations/spacing.mdx`), a text
size outside the scale, an opacity of its own instead of `bui-disabled`,
a component root without its `data-slot`, and motion that breaks the rule
above: a transition without named properties, the kit's curve, or a
duration of 300 ms or under, or keyframes that don't step.

`foundations/story-options.test.ts` fails when a story's control offers
other `options` than the prop's union, and when the `Overview` (what the
visual tests compare) leaves one of those values out.
